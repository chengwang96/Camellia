# 五分钟预览超时核查

## 原因

用户报告 `50be9bfb-a3b5-4240-b1c0-21932e420bc7` 使用 Ollama Cloud 的 `deepseek-v4.1-flash`，整轮从 2026-09-16 16:13:38 到 16:16:22（UTC+8），实际耗时 **163.867 秒**。

当时预览给每题固定 75 秒。Codex 前两题分别耗时 50.950 秒和 35.266 秒，多文件 invoice 题在 75.524 秒停止；整轮五分钟额度仍有约 136 秒。保存的文件变更只有 `money.cjs`，`invoice.cjs` 尚未修改，不能视为已经完成却被评分器误判。最后一个 API 请求因停止被取消，缺少用量不是已证实的提供方故障。旧记录未保存请求时间线，无法精确拆分当时的 API 等待和工具执行时间。

问题是预览把整轮预算切得过细：某题达到 75 秒便停止，即使整轮还有大量时间。

## 修复后的时间规则

- 五个引擎并行，各自顺序执行同样三道题。
- 每个引擎的三题共用 **270 秒**，从整轮开始计算；较慢的题可以使用剩余时间。
- 第 270 秒停止仍在执行的 agent，未开始的题标记为 Not started。
- 整轮仍有 **300 秒**截止时间，最后 30 秒留给独立验证和清理。取消进程可能额外需要几秒。
- 超时仍按原规则记零分，未开始的题没有分数；题目、检查和评分权重未变。历史记录保留原始时限及分数。
- 详情新增实际可用时间、API 请求耗时、工具活动和超时瞬间的状态；异常退出也保留已修改文件和可获得的部分回复。

这只是更合理地使用有限预算，不能保证慢 API 或所有模型都在五分钟内完成。

## 实测

使用用户已授权的 Ollama API，模型 `deepseek-v4.1-flash`，五个实际原生引擎并行，每题一次、250K 已报告 token、最多 40 次 API 请求。两轮数据均写到独立的本地审计目录，未覆盖用户历史报告。

第一次试验使用每题新增 90 秒、前题剩余时间供后题使用的中间方案。Codex 三题通过，但 Claude 和 Antigravity 第一题仍在 90 秒被停止；整轮不足三分钟。新增时间线记录两者都在等待 API 响应，其中各有一次请求耗时超过 43 秒。由此改为三题直接共享 270 秒。

最终方案实测报告：`133c708e-43fa-4f5f-b5ca-4d3c39c27803`，从 16:41:53 到 16:43:46（UTC+8），**112.543 秒结束，15/15 项完成，0 次超时、0 次运行错误**。

| 引擎 | 检查完成度 | 整题通过 | invoice 耗时及结果 |
| --- | ---: | ---: | --- |
| Claude Code 2.1.270 | 100 | 3/3 | 39 秒，11/11 |
| Codex CLI 0.147.0 | 97.2 | 2/3 | 56 秒，11/11 |
| DeepSeek Harness 0.1.5-rc.1 | 97.2 | 2/3 | 25 秒，11/11 |
| Kimi Code 0.43.0 | 100 | 3/3 | 26 秒，11/11 |
| Antigravity SDK 0.1.16 | 100 | 3/3 | 35 秒，11/11 |

这一轮 Codex 和 DSH 的文本规范化都得到 11/12：输入 `a\u1ab0b` 的预期输出是 `ab`，实际为 `a-b`。这是组合字符范围遗漏，和超时不同。全轮已报告用量 1,545,089 token，没有未报告用量。

最终原始数据位于 `dist/benchmark-audit/live-1789548113569/`；中间方案数据位于 `dist/benchmark-audit/live-1789547689987/`。单次实测不能保证今后不出现超时，API 延迟和生成过程会波动；确定性的计时回归覆盖第一题 110 秒、末题 100 秒仍可完成，以及 270 秒停止与 300 秒整轮截止。

## 验证范围

- 跑分与 API 路由自动检查：共享时间、并行队列、取消清理、用量记账、请求诊断、未开始题不计分。
- 无 API 的无界面 Chromium 测试：预览/全集/自定义切换、历史时限显示、超时详情和窄窗口布局。
- 两次真实 API 试验；最终方案 15 项全部结束。
