## 已确认的集成问题

Camellia 的 DSH 聊天和 benchmark 配置把单次输出固定在 **8,192 Token**，而固定版本 DSH `0.1.5-rc.1` 的原生提供方默认值是 **32,768**。科研任务的推理会占用输出 Token，可能在尚未生成代码前就达到 8K。

使用真实 DSH、仅连接本地模拟 API 的复现结果：

| 情形 | 请求中的 max_tokens | 提供方结束原因 | 原生结果 |
| --- | ---: | --- | --- |
| 旧配置 | 8192 | length | 退出码 1，没有正常完成 |
| 修复配置 | 32768 | stop | 正常完成 |
| 修复配置仍被截断 | 32768 | length | 退出码 1，正确保留截断诊断 |

DSH headless 对这种停止不会打印明确的错误行，只把推理流写到 stderr。旧适配器把 stderr 最后 1,000 字符当成错误，用户因而看到不完整的思考文本。历史 7 个不明退出中，6 个仅有 3 次请求、累计约 8.37–8.41K 输出 Token；另一个在较多请求后结束于推理中途。这些表现高度符合单次输出截断，但旧报告没有记录 finish_reason，不能把全部 7 个逐一判定为已证实的相同原因。

修复内容：

- DSH 聊天和跑分均恢复原生 32,768 单次输出默认值；每题总预算仍独立生效。
- 路由层保存结束原因、实际单次上限、是否包含工具；评分报告记录原生退出码。
- 标题生成可能在任务之后发送 64-Token 请求，诊断分别保存任务响应与辅助请求，避免标题覆盖主要错误。
- 输出截断显示为 **Output limit**，并说明它和每题时间/Token 上限的区别。
- 不再把任意推理文本当成异常；可恢复的配额错误保留计数，成功重试后不继续冒充终止原因。
- 结果页展示运行错误和配额提示；历史报告与原始分数保持不变。
