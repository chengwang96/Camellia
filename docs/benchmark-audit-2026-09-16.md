# Benchmark 核查记录（2026-09-16）

## 结论

重复同分有多种来源。本次确认了评测实现问题和 SciCode 原始题库问题，不能据此断定某个模型或 harness 的能力。计分器仍按通过的检查数计算部分分，不会为了消除同分而放宽官方数值容差。

## 已确认的问题与处理

| 问题 | 复现证据 | 处理 |
| --- | --- | --- |
| 旧版 SciCode 比较函数未加载 | 历史报告五个引擎都是 4/14，错误为 `ModuleNotFoundError: No module named 'scicode'`。同一批答案在已修复的评分器下是 7/14。 | 之前的修复已确认有效；当前评分器保留调用模型前的依赖和答案检查，环境错误不记为答错。 |
| SciCode #46 要求特定随机轨迹 | 对五份已保存答案采用官方子问题内顺序复算，得到 7、7、7、6、7 / 14。仅把 DSH 的随机接受条件从 `u < p` 换成 `1-u < p`，7/14 变成 14/14。两者接受概率相同。独立写的采样对照也复现了这两个分数。 | 原始题目和分数保留；短题库不选这道题，完整题库明确标注局限。 |
| SciCode #15 题面遗漏物理常数 | 固定版本的主问题及 15.1 均写成 `hbar = × 10^-34`，缺少系数。实测有引擎花时间寻找原始资料。 | 短题库不选这道题；完整题库显示题面缺陷提示。没有把推测的常数偷偷加进题目。 |
| 科学任务自测无法正常导入本地文件 | 旧提示要求 Python `-I`，它会移除脚本目录，普通的 `from solution import f` 会失败。 | 模型自测改用 `-E -s -X utf8`，评分器仍用 `-I`。加入真实 Python 导入回归检查。 |
| 测试拆分改变共享状态 | 旧适配器逐条启动进程，重置官方案例间可能共享的变量和随机状态。 | DS-1000 保留原执行循环，SciCode 每个子问题内保留案例顺序及共享命名空间；仍逐条记录部分分。共享变量及连续随机抽样回归通过。 |
| Codex 超时清理可能卡住整轮 | 实测进程退出码已为 1，但输出管道未关闭，`close` 未触发，报告迟迟停在 Running。释放遗留管道后立即完成清理。 | 终止原生进程后关闭管道，避免无限等待；已退出的 PID 不再发送终止请求。补了复现该状态的回归测试。 |
| 保存证据可能遗漏完整答案 | 旧文件差异限制每文件 32 KB，且可能先收集到二进制缓存，而评分器接受最多 1 MiB 的 Python 源码。 | 优先保存完整 `solution.py` 及 SHA-256，跳过二进制缓存；题库抽样变化后仍可按保存的题目 ID 离线重判。 |

新版评分器标识为 `python-checks-3`。SciCode 抽样策略为 `camellia-sample-2-known-issues-last`，完整测试集仍为 65 题。历史报告保留原题目 ID 和版本。仅两道已核实的问题题目移至抽样末尾；其他题目并不因此被宣称全部正确。

- 186 项 Node 自动测试通过。
- 真实 Python 检查：SciCode 65 道测试集题目的依赖和数值答案键；DS-1000 七个库各一个官方参考答案；SciCode 三道开发集参考题；#46 等价采样对照；错误代码、共享状态、UTF-8、超时和取消。另静态核对了 DS-1000 全部 1,000 题的执行循环结构及 1,620 个执行案例的计数，未发现不兼容或计数错误。
- 五个真实原生 harness 使用本地模拟 API 的并行文件写入、独立计分、模型固定、用量隔离和取消测试通过。模拟 API 的结果不作为模型成绩。

- Windows 安装目录打包通过，99 个应用源文件与包内内容一致。

## 真实 API 测试

经用户授权，只使用已配置的 Ollama `deepseek-v4.1-flash`。五个原生版本与用户运行中的应用一致：Claude Code 2.1.270、Codex CLI 0.147.0、DSH 0.1.5-rc.1、Kimi Code 0.43.0、Antigravity SDK 0.1.16。

第一轮为 3 分钟限制：SciCode #15 的五次尝试均超时；DS-1000 #354 的 Antigravity 通过，其他四个超时；#160 的 Claude、Codex、Kimi 通过，DSH、Antigravity 超时。共 94 次请求，1,380,740 个已报告 Token。

第二轮用修正后的 Python 自测参数复现了 #15 的题面缺陷和 Codex 清理卡住的问题。五次尝试均超时，清理恢复后主动结束该诊断轮，未继续后续题目。共 32 次请求，528,746 个已报告 Token。

最终轮使用修复版、SciCode #74、每次 5 分钟，五个引擎并行：

| Harness | 原始运行结果 | 原始计分 | 事后离线检查保存的答案（不计入原始成绩） |
| --- | --- | --- | --- |
| Claude Code | 188 秒完成 | 3/3，100 分 | 3/3 |
| Codex CLI | 超时 | 0 分 | 2/3 |
| DSH | 超时 | 0 分 | 3/3 |
| Kimi Code | 超时 | 0 分 | 3/3 |
| Antigravity SDK | 超时 | 0 分 | 2/3 |

该轮共 46 次请求，738,248 个已报告 Token；所有超时在清理后正常结束，整轮状态为 Completed。日志中能看到 Codex 重复执行有数组形状错误的自测；DSH 继续推敲 QR 分解的符号约定并补充自测。保存的答案检查说明，“代码已经正确”和“在时间内完成原生会话”是两件不同的事。结果体现了工具、自测及停止行为的差异，不能据一道题宣布某个 harness 最强。

本次共 25 次真实任务尝试、172 次 API 请求、**2,647,734 个已报告 Token**（包含缓存输入）。18 次请求未报告完整用量，主要发生在取消/超时期间；这些数字不是精确账单。诊断 JSON 已检查不含已配置的 API key。

原始报告及答案在 `dist/benchmark-audit/live-1789509436349/`、`live-1789509995020/` 和 `live-1789510600958/`。最后一个目录的 `postmortem.json` 单独保存离线检查，未覆盖超时分数。

这些超时保持为超时和零分，没有用重试的成功结果覆盖。应用中另有完整题库跑分并行消耗同一供应商额度，不同诊断轮的题目及时间限制也有变化，因此这些轮次不能作为性能排行榜或修复前后的严格因果比较。

## 如何解读同分

分数由模型、harness、题目及预算共同决定。同一模型可能在多个 harness 中选择相似算法；同一组苛刻或有缺陷的断言也会让它们同时失败。Harness 仍会影响工具选择、文件修改、自测、纠错和任务完成时间。本次没有做多模型、多题库、多次重复的因子实验，不能量化哪一部分贡献最大。

科研函数实现题主要观察科学推理和数值实现。比较 harness 的工具协作能力，还需要包含仓库级修改、多文件调试和长任务的题目。当前这些小规模控制测试用于排除集成问题，不能代表完整的 harness 排名。
